SECURITY REQUIREMENTS (RISK ASSESSMENT)

  Assets: traders' accounts and sessions; their business details and
  books (customer names and amounts stay private to the trader); photos
  and documents; suppliers' catalogues, prices and stock; orders, their
  money and their payment status; invoices and receipts; the two-sided
  record (credit given, stages a client signed off).

  Main risks: account takeover (guessed, leaked or reused passwords, a
  stolen phone, a stolen token); fishing for which emails have accounts;
  one user reading another's data (IDOR); injection (SQL, email header,
  template, script); junk or malicious input crashing the service;
  forged callbacks from our providers; malicious or oversized uploads;
  personal data leaking into logs; automated abuse of sign-in and search;
  a phone changing a price or a total; one order placed twice on a bad
  signal; the same last stock sold twice; a forged "payment complete";
  a supplier feed smuggling spreadsheet formulas or foreign image links;
  a supplier marking itself verified; guessable invoice links.

  Requirements we set ourselves:
  - The server trusts nothing the phone claims: identity only from a
    verified token; verification results (e.g. the company check) set
    only by the server; upload details taken from the storage provider,
    not from the phone.
  - POPIA: collect only what we can verify or need; consent versions
    recorded at sign-up; users can download their data and close their
    account; unconfirmed sign-ups deleted after 7 days.
  - We never hold money: payments go through a licensed provider
    (PayFast); card details never touch our systems.
  - Honest proof of payment: every order says what backs its money --
    verified by PayFast, cash confirmed by both sides, or cash not
    confirmed -- and totals are never mixed, so a cash claim can't pass
    for provider-verified money.
  - The server prices every order from its own catalogue; the phone only
    says which products and how many.


THREAT MODELLING & DESIGN REVIEW (STRIDE -- what is built)

  Spoofing
  - Passwords: bcrypt; 8-64 characters and at most 72 bytes, with upper,
    lower, digit and symbol, checked by the server (not only the app).
  - Two-factor sign-in: on a phone not seen before, the right password
    only earns a one-time code by email, bound to a random challenge
    held by that phone; the phone is then trusted with a random token
    (only its HMAC stored), revocable from the Security screen.
  - Lockout after 5 wrong passwords, revealed only to someone who then
    gives the right one.
  - No account enumeration: sign-up, sign-in, resend and forgot-password
    answer identically whether or not the email exists, with equal
    timing (a dummy password check runs for unknown emails).
  - Payment notifications: an order becomes PAID only if PayFast's
    notification passes all four checks -- our MD5 signature with a
    secret passphrase, the sender is one of PayFast's own servers, the
    amount equals the order to the cent, and PayFast answers VALID when we
    post it back. Returning from the payment page proves nothing.
  - Suppliers can't verify themselves: a feed claiming "verified" is
    refused; only our own check sets it.

  Tampering
  - Append-only audit trail, enforced by database triggers (rows cannot
    be updated or deleted, not even by the app).
  - Provider callbacks (Cloudinary) verified by signature, refused when
    older than 2 hours (replay) -- a forged call gets 401 (tested live).
  - Uploaded files are checked with the provider itself before they are
    accepted: real size and URL, and the upload must have been started by
    the same user for the same purpose.
  - Prices can't be tampered with: an order request carrying a price or a
    total is refused; each order line keeps a snapshot of the price at
    order time, so a later price change never alters a placed order.
  - Stock is held with one atomic database update that succeeds only if
    enough is left, so the same last item can't be sold twice; stock goes
    back when an order is cancelled, rejected or lapses.
  - A retried "place order" (Idempotency-Key) returns the first order
    instead of creating a second one; a key reused for a different order
    is refused.
  - Payment links and client sign-off links are 256-bit tickets stored
    only as HMAC-SHA256 hashes, short-lived and revoked by a newer link.
    Invoice and receipt downloads use links signed with a server key that
    expire after 10 minutes and are valid for one document only. Every
    document carries a QR code to a signed public check page, so a forged
    or altered invoice is caught; that page shows no personal details.
  - Builders' stage photos: the server records its own time and a SHA-256
    fingerprint of the stored file, so a swapped or back-dated photo is
    detectable; camera only, never the gallery.
  - Supplier data feeds are checked row by row: unknown columns refused,
    money parsed exactly, barcodes' GS1 check digits verified, cells that
    start with = + - @ refused (spreadsheet-formula injection), image
    links accepted only from our own image service (no tracking pixels or
    foreign content), 5 MB / 5,000-row caps; bad rows reported by row
    number, never silently dropped.

  Repudiation
  - Every identity action is audited: who, which session, which phone,
    success or failure and why -- never passwords, codes or tokens.
  - Orders keep an append-only history of every step and who made it
    (trader, supplier or system); order, payment, feed-import, connection
    and credit-book events are audited without names or phone numbers.

  Information disclosure
  - Secrets stored only as hashes: bcrypt for passwords; HMAC-SHA256 for
    email codes, reset tickets and trusted-phone tokens.
  - No secrets in logs, even in development (an automated test fails the
    build if a code ever appears in the logs).
  - Security headers on every response: no content sniffing, no framing,
    no referrer, no caching. The password-reset page carries the ticket
    with no-referrer and no-store.
  - Provider keys (Mapbox, Cloudinary, PayFast merchant key and
    passphrase) stay on the server; the app never receives them. Storage
    folders use HMAC keys, never database ids.
  - Traders see only what they need: a supplier's orders email, payout
    account, VAT and legal details are never sent to the app; product
    codes, barcodes and exact stock numbers never leave the server (only
    "in stock / low / out").
  - From a payment notification we keep amounts, status and PayFast's
    reference -- not the payer's name, email or card.

  Denial of service
  - Rate limits on every sensitive route (sign-in 5/min per IP+email,
    sign-up 5/hour, codes, resets, search, uploads, orders, payments,
    catalogue search), 1 MB request cap, a daily upload quota per
    account, and a daily cap on company checks.
  - JSON nested deeper than 32 levels is refused before any route runs
    (found by our own hostile-input tests: a deeply nested body crashed
    every route; now fixed and tested at 100,000 levels).

  Elevation of privilege
  - Every route pins who may call it (signed-in trader, supplier, or a
    public page holding a one-time ticket).
  - Every query is scoped to the signed-in user from the token; a user id
    from the request is never trusted (IDOR tests prove another trader
    gets nothing: orders, credit book, jobs, connections, documents, the
    order book, the bin, builder profiles and help posts). Ids are random
    UUIDs, and "not yours" answers exactly like "doesn't exist" (404), so
    nobody can even learn that someone else's record exists.
  - Order book orders made offline: the phone's id is kept as a separate
    key, unique per trader, and always looked up together with the
    signed-in trader, so two traders' phones can never collide and a clash
    can't reveal another trader's order. The server prices every line from
    the menu price valid at the time of the order -- never the phone's.
  - Deleting moves an item to a bin (restorable for 30 days, never
    erased); payments already recorded and stages a client confirmed stay.
    Binning a job revokes the client sign-off links not yet answered, so a
    job binned by mistake can't be confirmed.
  - A trader can only order from a supplier they've connected to; cash is
    limited to R1,000 per order and 2 waiting orders (a cash order costs
    nothing up front, so this caps the damage of fake orders); digital
    orders can't be cancelled by the trader and lapse unpaid after 24 h.
  - Developer tools (loading test suppliers, moving an order as the
    supplier) refuse to run outside development.
  - Sessions: 15-minute access tokens; refresh tokens rotate, and reusing
    an old one ends the session (theft detection); every request checks
    the session is still live, so sign-out and password changes cut
    access off immediately.
  - The identity code is sealed: an automated architecture test fails if
    any other part of the system reaches into its internals.


DEVELOPMENT (SECURE CODING PRACTICES)

  - SQL injection: all database access goes through SQLAlchemy with
    bound parameters; no SQL is ever built from user input. Tested with
    injection strings in every text field.
  - Mass assignment: strict request schemas reject unknown fields, so a
    client can't set a field it shouldn't (e.g. its own verified status).
  - Input hygiene: text is Unicode-normalised and trimmed; control,
    invisible and right-to-left-override characters are refused; a
    request carrying a NUL character is refused before any code runs;
    names must be real names (letters; no emoji; business names without
    digits); money is integer cents; coordinates must be real numbers
    inside range (NaN/Infinity refused).
  - Injection into emails: email templates escape user text; email
    addresses are validated so header injection (CR/LF) can't pass.
  - Configuration: secrets only from environment variables; production
    refuses to start with short secrets (< 32 characters), without real
    email, without media keys, or without an https public address.
  - Process: every change on a feature branch; pull requests reviewed by
    the lead before merging into main; all AI-assisted code is reviewed
    by a team member before merge; database migrations reviewed and
    checked against the models.


SECURITY TESTING (automated, run before every merge)

  - 1,052 backend tests and 147 app tests, including hostile-input suites
    for identity, the credit book, jobs, the order book and the builder
    network: malformed and
    injected emails (SQL, CR/LF header injection, script), emoji,
    control and invisible characters, template injection, wrong JSON
    types, broken bodies, NaN/Infinity, very long values. Rule: refuse,
    never crash, never accept junk, never leak whether an account exists.
  - These tests found and we fixed real bugs: long/emoji passwords
    crashing bcrypt (over 72 bytes), a NUL character crashing the
    database write, invisible characters accepted as a name, and deeply
    nested JSON crashing every route.
  - Design review found: behind a reverse proxy (Cloudflare) every caller
    would look like 127.0.0.1, so one attacker could use up the sign-in and
    code limits for everyone; and the audit trail took the first
    X-Forwarded-For entry, which a caller can fake. Fix in progress before
    any proxy goes live: one trusted client-address helper, switched on
    only where the server is reachable solely through Cloudflare, with
    tests that a forged header is ignored.
  - Commerce: the phone can't send prices; out-of-stock holds nothing;
    a retried order lands once; cash limits; cancel rules; unpaid orders
    lapse and give stock back; every PayFast check refuses a forged
    notification on its own (bad signature, wrong passphrase, wrong
    sender, wrong amount, not confirmed); payment links used up or
    replaced; invoice links altered, expired or for another trader get
    nothing. The PayFast sandbox accepts our signed payment.
  - IDOR, rate-limit, lockout, two-factor, refresh-token reuse, password
    reset (one use, expiry), account closure, data export (no secrets),
    audit-trail immutability, and architecture-boundary tests.
  - End-to-end: a script checks the real media provider (signed upload,
    verification, forged callback refused, genuine one accepted,
    clean-up); browser runs of sign-up, two-factor, profile and restore.


ASSESSMENT & SECURE INTEGRATION -- PLANNED (not built yet)

  - Cloudflare in front of the API (free plan; settings written down):
    a named Cloudflare Tunnel so the server has no open port (it listens
    on 127.0.0.1 only); Always HTTPS, TLS 1.2+ and HSTS; the managed WAF
    ruleset plus custom rules (skip only our signed PayFast and Cloudinary
    callbacks; block scanner paths such as /.env and /.git; block unusual
    methods; allow only our own paths); a flood cap on sign-in; Turnstile
    on the pages opened from links (sign-off, password reset, invoice
    check); Access in front of staff-only tools. Bot Fight Mode stays off
    on the API because it would block our app and payment notifications.
    Cloudflare will be named as an operator in the privacy policy (POPIA).
    Today a fixed https tunnel (ngrok) is used for payment notifications
    and links.
  - Shared rate-limit store (Redis) so limits hold across servers.
  - Malware scanning of every upload (Cloudinary + Perception Point) with
    files hidden until approved -- the approval path is built and tested;
    switched on once the add-on is enabled.
  - Payments: PayFast split payments straight to each supplier's own
    PayFast account (built behind a switch; needs each supplier's
    merchant id), and automated refunds.
  - Supplier system integration (ERP): scoped, hashed API keys with
    rotation and revocation, signed requests, per-key limits.
  - Two-sided proof: records sealed with hashes and phone-held signing
    keys (the server check for phone keys is built; the phone side comes
    with the next app build).
  - Refusing known leaked passwords; dependency and secret scanning in CI;
    an external penetration test and a POPIA legal review before launch.

  Honest limits: a record proves what both sides confirmed, not that it
  was true; email as a second factor is only as safe as the email
  account; a signed-link confirmation is weaker than two signed phones,
  and we label it as such.
