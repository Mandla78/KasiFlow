4a. EDITING THE PROFILE SAVES FOR REAL, AND SAYS SO
---------------------------------------------------------------------------
  - Each edit screen (Your business, Where you are, What you buy,
    Registration) in EDIT mode saves on "Save" with a direct call:
      businessProfileApi.save(only that section) -> wait for the answer
      -> success: update the session from the SERVER's answer, show
         "Saved" (a short toast), go back
      -> 422: show the server's message under the field, stay
      -> offline / 5xx: "Couldn't save. Check your connection and try
         again." with the button enabled; nothing lost on screen
    Onboarding keeps the quiet background save (it already works there).
  - Send only the changed section, not the whole profile (smaller, and
    one bad field in another section can't block this save).
  - The quiet sync gets a visible state: if the last save failed, the
    Business profile screen shows one line "Some changes aren't saved
    yet. Tap to try again."
  Backend: no change needed (PATCH already takes sections). Add tests:
    a PATCH of one section leaves the others unchanged; 422 names the
    field.

4c. DELIVERY ADDRESSES: STORED, CHOSEN AT CHECKOUT
---------------------------------------------------------------------------
  Backend (new, informal_trader/business_profile or its own feature
  informal_trader/delivery_addresses -- Question 2)
    table trader.delivery_addresses  (migration: next free number after
      the notifications 0023 and "I paid the cash" 0024 -> 0025; check
      origin first)
      id uuid, user_id (FK, cascade), label CleanText 1..30 ("Shop",
      "Home", "Site on Main Rd"), address_text 5..300, latitude,
      longitude (numeric, SA bounds check), is_default bool,
      created_at, updated_at, deleted_at (soft delete).
      Max 5 per trader. One default per trader (partial unique index).
    GET    /me/delivery-addresses              60/min
    POST   /me/delivery-addresses              20/min, Idempotency-Key
             {label, address_text, latitude, longitude, is_default?}
    PATCH  /me/delivery-addresses/<id>         20/min
    DELETE /me/delivery-addresses/<id>         20/min (soft)
    POST   /me/delivery-addresses/<id>/default 20/min
    All scoped to current_user(); someone else's id = 404; strict
    schemas (unknown fields 422); the 6th address = 409 "You can keep 5
    addresses. Remove one first."
    The business's own location stays the "Business address" (from the
    profile); saved addresses are extra places.
    Orders: POST /me/orders may send delivery_address_id instead of a
    one-off address+pin; the server looks it up FOR THIS USER (404 if
    not theirs) and still checks the supplier's delivery radius. The
    one-off address stays allowed.
    Audit: delivery_address.added / removed (ids only, no address text).
  App
    More -> Delivery addresses -> list (Business address first, then
    saved ones, default marked) -> Add (the existing AddressPickerField:
    search + map pin) -> label -> Save. Edit, remove (confirm), make
    default. Subtitle on More: "Business + <n> saved".
    Checkout: "Deliver to" offers Business address, the saved ones, or
    "Somewhere else" (as now; with "Save this address" ticked it's added
    to the list).
  Tests: IDOR on every route, the 5-limit, one default, soft-deleted
  ones never listed or usable, bad coordinates (outside SA, NaN, huge),
  hostile labels, an order with someone else's address id = 404, an
  address outside the radius refused.
