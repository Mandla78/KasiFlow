WHAT WE WANT
  Notifications that are REAL: written by the server when something really
  happens, read from the database, marked read on the server, and showing
  up on the phone within seconds without the trader pulling to refresh.
  Two tabs:

    ORDERS  everything about orders with suppliers: sent, waiting for
            payment, paid, accepted, rejected, on its way, ready to
            collect, delivered, collected, lapsed.
    INBOX   everything else: account and security (a new phone signed
            in, password changed, other phones signed out), and the
            tools (a client confirmed a job stage, amounts don't match).

  Every notification comes from a TEMPLATE (never free text typed at the
  call site). Tapping one opens it in a pop-up sheet with the full text
  and a button to the real thing (the order, the job). Opening it marks
  it read -- on the server.

  Branch: risuna/notifications (from the latest main; git pull first).
  Same rules as always (11_AI_AGENT_BRIEF.txt, 12_DEFINITION_OF_DONE.txt):
  CONTRACT first (feedback/CONTRACT_notifications.txt), Mandla approves,
  then build. Small commits.

1. DESIGN
---------------------------------------------------------------------------

  1a. Where the code lives
    backend/src/domains/platform/notifications/{api, models,
      repositories, schemas, services, templates.py}
    (schema "platform" exists already.) It LISTENS to
    shared.notifications; it never imports orders, auth or jobs, and they
    never import it (tests/architecture/test_domain_boundaries.py).

    Change shared/notifications/notification_types.py (Mandla's file --
    say so in the PR) so an event carries a TEMPLATE KEY + PARAMS instead
    of ready-made text:
        NotificationEvent(recipient_user_id, template, params: dict,
                          link: {"type": "order", "id": "..."} | None,
                          dedupe_key: str | None)
    Tabs become ORDERS and INBOX (rename STOCK_ORDER). The template decides
    the tab, the icon and the words, so every caller stays one line:
        publish_notification(NotificationEvent(user.id, "order.accepted",
            {"reference": o.reference, "supplier": o.supplier_name},
            link={"type": "order", "id": str(o.id)},
            dedupe_key=f"order:{o.id}:accepted"))

  1b. Templates  (services/templates.py -- one dict, reviewed like copy)
    key -> tab, icon (Feather name), title, body, level (info | action |
    security). Text written the way a trader speaks. Params are plain
    values the SERVER fills (reference, supplier business name, rand
    amount already formatted); never user-typed text.

      ORDERS
      order.sent             send          "Order sent to {supplier}"
                                            "{reference} · {total}. Waiting for them to accept."
      order.awaiting_payment credit-card   "Pay to send your order"
                                            "{reference} · {total} to {supplier}. Pay within 24 hours."
      order.paid             check-circle  "Paid. {supplier} has your order"
                                            "{reference} · {total} paid in the app."
      order.accepted         thumbs-up     "{supplier} accepted your order"
      order.rejected         x-circle      "{supplier} can't do this order"
                                            "{reference}. Your stock hold is released."
      order.on_its_way       truck         "Your stock is on its way"
                                            "{reference} from {supplier}.{cash_line}"
      order.ready            package       "Ready to collect at {supplier}"
      order.delivered        check         "Delivered: {reference}"
      order.collected        check         "Collected: {reference}"
      order.expired          clock         "Order {reference} lapsed"
                                            "It wasn't paid in time. Nothing was charged."
      INBOX
      account.new_phone      shield        "A new phone signed in"
                                            "If this wasn't you, change your password now."
      account.password_changed  lock       "Your password was changed"
      account.phones_signed_out log-out    "Other phones were signed out"
      job.stage_confirmed    check-square  "{stage} confirmed by your client"
      job.amounts_dont_match alert-triangle "Amounts don't match on {stage}"
      job.not_yet            message-circle "Your client says {stage} isn't done yet"

    {cash_line} = " Have {cash} cash ready." for cash orders, else "".
    Security alerts NEVER include an IP address, a place, an email or
    the device's name (no attacker hints, CLAUDE.md).
    Job alerts NEVER include the client's name or phone (use the stage
    and job title only).

  1c. Table  platform.notifications   (migration 0023 -- check origin
      first; rename if someone got there)
      id uuid pk, user_id uuid not null (FK identity.users, on delete
      cascade), tab CHECK (orders, inbox), template varchar(60),
      params jsonb, link_type varchar(30) null, link_id uuid null,
      dedupe_key varchar(120) null, created_at timestamptz, read_at
      timestamptz null.
      UNIQUE (user_id, dedupe_key) -- a retried request never makes two.
      INDEX (user_id, tab, created_at desc); partial index where read_at
      is null for the counts.
      Store the template key + params, NOT the rendered text: the words
      can be fixed later without touching rows. Render on read.
      Keep 90 days (a scheduled clean-up job, like expire_unpaid).

  1d. Settings  platform.notification_settings (same migration)
      user_id pk, orders bool default true, jobs bool default true.
      Security alerts (account.*) are ALWAYS on and can't be switched
      off -- show them locked in the app with "Always on for your
      safety". When a type is off, the listener simply doesn't write the
      row.

  1e. Real time -- honest version for this weekend
      The app POLLS a tiny endpoint:
        GET /me/notifications/unread   -> {orders: 2, inbox: 1, latest_id}
      every 20 s while the app is open and in front (AppState "active"),
      immediately when it comes back to the front, and when the
      Notifications screen gets focus. When latest_id changes, refetch
      the list. That is seconds-fresh, cheap (one indexed count) and
      works through ngrok today.
      NOT this weekend (list in "Not done"): phone push notifications
      (expo-notifications = a new native build + Firebase keys) and
      server-sent events / websockets (hold a server thread per phone).
      The API above is what push will use later, unchanged.


---------------------------------------------------------------------------
2. ENDPOINTS  (all @auth_required, scoped to current_user(); not yours =
   404; marshmallow unknown=RAISE; rate limits keyed on the user)
---------------------------------------------------------------------------

  GET  /me/notifications?tab=orders|inbox&before=<id>&limit=20   120/min
       {notifications: [{id, tab, icon, title, body, level, link,
        created_at, read}], next: <id>|null}   newest first
  GET  /me/notifications/unread                                   240/min
       {orders, inbox, latest_id}
  POST /me/notifications/<uuid:id>/read                            120/min
       -> {notification}. Idempotent (already read = 200, same row).
       Someone else's id = 404.
  POST /me/notifications/read-all   {tab: orders|inbox}             30/min
       -> {marked: n}. Only that tab, only mine.
  GET  /me/notification-settings                                   60/min
       {orders: true, jobs: true, security: true (read-only)}
  PUT  /me/notification-settings   {orders?: bool, jobs?: bool}     20/min
       "security" in the body = 422 (unknown field).

  No endpoint creates a notification. Only the server does, through
  publish_notification. There is no delete (read is enough).

3. THE HOOKS (one line each, in Mandla's domains -- list them in the PR)
---------------------------------------------------------------------------

  order_service.place()          order.sent | order.awaiting_payment
  order_service.supplier_move()  order.accepted / rejected / on_its_way /
                                 ready / delivered / collected
  order_service.mark_paid()      order.paid
  order_service.expire_unpaid()  order.expired (one per order)
  auth_service._tokens(new_device)   account.new_phone
  auth_service.change_password()     account.password_changed
  auth_service.sign_out_other_phones() account.phones_signed_out
  sign_off_service.answer()      job.stage_confirmed / amounts_dont_match
                                 / not_yet  (to the BUILDER)

  Publish AFTER db.session.commit(), never before: a rolled-back order
  must never leave an alert behind. dedupe_key on every one
  (f"order:{id}:{status}", f"job:{stage_id}:{sign_off_id}", ...).
  publish never raises, so the real action can't fail because of an alert.

6. SECURITY BY DESIGN (put in the PR)
---------------------------------------------------------------------------

  IDOR     every query WHERE user_id = current_user().id; 404 for others
  Input    strict schemas; tab is an enum; limit capped at 50
  Content  templates only, server-filled params; no user-typed text in
           titles; no IP / place / email / device name in security
           alerts; no client name or phone in job alerts
  Abuse    rate limits above; dedupe_key unique; 90-day clean-up
  Audit    notification.settings_changed (which switch, on/off). Reading
           isn't audited (too noisy, not disputable).
  Honest   an order alert is not proof of payment: the text says "paid in
           the app" only after the provider-verified path (mark_paid)
